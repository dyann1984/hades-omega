# HADES OMEGA — Informe de fase 3

Fecha: 27 de octubre de 2026. Rama: `codex/recovery-omega-20261026`. Inicio: `9d1fe94`. El directorio de recuperación anterior se conservó sin seguimiento. No se desplegó ni se modificaron credenciales existentes.

## Estado y resultado
**Fase incompleta; no apta para producción.** Hay una misión local real de alcance deliberadamente limitado, con aprobación, persistencia SQLite y una prueba de navegador reproducible. No existe aún un sistema empresarial completo de inicio de sesión, revocación, cancelación o aislamiento integral de toda la interfaz y las rutas antiguas.

## Arquitectura y cambios
- Las misiones nuevas del API llevan `ownerId` obtenido del JWT. Las misiones antiguas sin propietario quedan accesibles solo a ADMIN, sin asignarles un dueño inventado. ADMIN puede leer todas las misiones y eventos y decidir aprobaciones; los demás roles solo leen misiones propias. Las respuestas de misiones ajenas son 404. Las rutas globales de agentes, CERBERUS y lista de aprobaciones exigen ADMIN. En WebSocket los eventos de misión/tarea requieren propietario o ADMIN; los eventos globales sensibles son solo ADMIN. La sesión y el rol se verifican en cada evento.
- El orquestador heredado sigue realizando trabajo de demostración; su planificación y agentes no se presentan como operaciones reales. Los eventos emitidos antes del primer guardado de una misión heredada no llegan al usuario no ADMIN.
- El repositorio operativo usa `better-sqlite3` y migraciones versionadas 1 y 2. Conserva misiones, tareas, auditorías, aprobaciones, eventos e idempotencia; la operación local tiene tabla específica. El JSON anterior no se elimina; antes de importar se copia a un respaldo y se importan registros en una transacción con comprobaciones de conteos y claves foráneas. Un error aborta la transacción y puede reintentarse; respaldos y diarios SQLite están ignorados por Git. No se han creado tablas de usuarios ni de agentes ni un migrador de identidad: los registros antiguos permanecen sin propietario. El estado en curso de misiones demo se guarda solamente al finalizar su procesamiento.
- La operación local `SHA-256` acepta una entrada UTF-8 acotada, la guarda en SQLite y crea una misión que espera aprobación. Solo ADMIN decide. Una transacción registra la decisión y estados de historial; si aprueba, calcula el hash real y guarda el resultado antes de confirmar; si rechaza, cancela el cálculo. La restricción única y el estado persistido impiden repetir una decisión. Una caída antes del commit revierte toda la transacción; una aprobación pendiente puede recuperarse tras reiniciar. Este mecanismo no es un ejecutor genérico de efectos externos ni garantiza exactamente una vez para futuras operaciones externas.
- El panel THRONE incorpora solicitud, revisión y resultado de esta operación. La entrada se almacena en texto claro para revisión y se muestra a ADMIN; no debe usarse para datos sensibles sin controles adicionales. El historial se consulta mediante API y las actualizaciones de tarea y misión se publican después de persistir.
- Se actualizó `@fastify/jwt` y `fast-jwt` para eliminar las alertas críticas de producción detectadas en la auditoría de npm. `npm audit --omit=dev` informa tres vulnerabilidades moderadas en React Router y uuid; la instalación completa también notificó vulnerabilidades en dependencias de desarrollo. Se requiere revisión y actualización compatible.

## Evidencia de seguridad y ejecución
- **PASS** pruebas REST: A y B crean misiones; las lecturas cruzadas de misión, tareas e informe devuelven 404; ADMIN puede leer una misión antigua sin propietario. No hay endpoints generales de modificación o cancelación para verificar acceso cruzado a esas acciones.
- **PASS** pruebas WebSocket: eventos de misión A y B se entregan solo a sus propietarios; ADMIN recibe eventos administrativos. La prueba utiliza repositorio simulado para las asociaciones, no reproduce todo el flujo en vivo ni las revocaciones.
- **PASS** pruebas SQLite: copia y conservación de JSON, importación una vez, preservación de tarea y aprobación al reiniciar, rechazo de JSON inválido, recuperación de aprobación pendiente, decisión concurrente única e historial de estados. No se realizaron pruebas de apagado forzado, concurrencia multiproceso o conjuntos reales de datos complejos.
- **PASS** `node scripts/e2e-phase3.cjs`: inicia Fastify, SQLite, dos servidores Vite y Edge headless con credenciales temporales; un operador solicita el cálculo, ADMIN lo aprueba, el navegador comprueba el SHA-256 y, tras reiniciar API, recupera resultado e historial. Una consulta REST de otro usuario recibe 404. Usa el backend y la base reales, sin mocks. No prueba un formulario de inicio de sesión: inyecta JWT temporales en Vite. Requiere Edge instalado o `HADES_BROWSER_PATH`, dependencias instaladas y el build de API actualizado.
- **PASS** suite general `npm test`: 56 pruebas (41 core, 13 API, 2 frontend), sin fallos; una prueba de integración posterior dentro del sandbox falló por `EPERM` al renombrar JSON temporal en Windows y pasó al repetirla con acceso local autorizado. Las pruebas de aislamiento y SQLite posteriores al ajuste de idempotencia también pasaron.
- **PASS** `npm run type-check`, build de API y frontend. **SKIPPED** lint: no hay tareas de lint configuradas. **NOT TESTED** inicio de sesión real, revocación, recuperación ante caída durante escritura, concurrencia entre procesos, cancelación general, carga, seguridad integral y E2E de flujos heredados.
- **BLOCKED** NEAR TESTNET real: integración y configuración autorizada no verificadas. MAINNET no se ejecutó. CHARON, PERSEPHONE, ELYSIUM y TARTARUS siguen usando datos o comportamientos de demostración.

## Riesgos y trabajo pendiente
El frontend heredado guarda datos en `localStorage` sin aislarlos por identidad; compartir navegador entre usuarios puede mostrar datos previos. El token de desarrollo se suministra mediante `VITE_DEV_TOKEN` y no es un mecanismo de sesión empresarial; faltan inicio/cierre de sesión, expiración visible y revocación. Los eventos de ejecución local son atómicos con el resultado, pero la orquestación demo general no tiene recuperación durable ni cancelación segura. Falta una política de retención y protección del contenido almacenado, esquema de usuarios y permisos, manejo completo de idempotencia de creación concurrente, pruebas de seguridad independientes y revisión de dependencias. No considerar demostrados todos los controles contra acceso ajeno o ausencia de vulnerabilidades críticas en los flujos completos.
